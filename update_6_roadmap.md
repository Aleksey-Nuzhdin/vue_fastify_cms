# Фаза 5 — синтез: дорожная карта улучшений VFC (2026-07-12)

Вход: `update_1_map.md` (у1), `update_2_architecture.md` (у2),
`update_3_security.md` (у3), `update_4_consistency.md` (у4),
`update_5_quality.md` (у5), `update_backlog.md` (bl) + решения по 4 развилкам
(у4, подтверждены владельцем 2026-07-10).

Правило работы (из `update_plan.md`): **один пункт → отдельная задача →
отдельный коммит.** Ничего не чинить пачками.

Шкалы: эффект — крит / высокий / средний / низкий;
стоимость — мин / низкая / средняя / высокая.

## Тезисы

- **Порядок этапов не случаен**: сначала среда и ворота (без них правки нельзя
  проверить), потом безопасность, потом мелкие реальные баги, потом крупные
  унификации, миграции данных — в конце, DX — фоном.
- **Самый выгодный пункт всей карты — SEC-2** (единая проекция user без
  `password`): один фикс закрывает сразу пять находок из четырёх отчётов
  (у3:H3, у3:L2, у2:п.2, у4:срез 1, у5:§3.1) — и утечку хешей, и «врущие»
  типы клиента.
- **zod не удалять** при чистке зависимостей: он мёртв сейчас (у5:§8), но
  именно на нём построен план валидации входа (VAL-1 ← у3:M1).
- ~~Одна развилка осталась открытой: SEC-4~~ — **решено владельцем
  2026-07-12: вариант A** (guard читает Redis-ключ access-токена — мгновенный
  отзыв при logout/logoutAll/смене пароля).
- Миграции данных (`vereficator`, `initionalValues`) — решения уже приняты
  (у4), но выполнять их стоит после стабилизации кода: каждое — сквозное
  переименование + миграция документов, откатывать больно.
